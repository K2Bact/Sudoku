## §1. Google Play 데이터 보안 — 판단이 안 끝난 것 둘

### 1-1. Play 게임즈 로그인이 "앱 외부 계정 로그인" 인가

**현재 답: `아니요`**

데이터 보안 2단계에 *"사용자가 앱 외부에서 만든 계정으로 앱에 로그인할 수
있나요?"* 가 있고 `아니요` 로 되어 있습니다.

그런데 앱에는 Play 게임즈 로그인이 있습니다.

```
src/services/playGamesService.js:81   signIn(interactive = false)
src/services/cloudSyncService.js      Play 게임즈 저장 슬롯에 백업
```

**질문:** 구글은 Play Games Services 로그인을 데이터 보안 양식의 "앱 계정 로그인"
으로 보나요, 아니면 플랫폼 서비스로 예외 취급하나요?

**왜 확신 못 하나:** `예` 로 바꾸면 **계정 삭제 수단 제공 요구**가 따라올 수
있습니다(현재 `제공 안 함`). 잘못 바꾸면 없던 의무가 생기고, 안 바꾸면 미신고일
수 있습니다. 양쪽 다 대가가 있어 추측으로 결정하고 싶지 않습니다.

**이게 결정적인 이유:** 앱은 계정 없이 100% 플레이 가능하고, Play 게임즈는
리더보드·클라우드 저장용 선택 기능입니다. 이 사실이 판정을 바꾸나요?

### 1-2. `기기 또는 기타 ID` 를 "공유됨" 으로 신고한 것이 맞나

**현재 답: `공유됨 ✔` · 목적 `광고 또는 마케팅`**

내 근거는 이랬습니다:

- 콘솔의 정의가 *"사용자 기기 내부 또는 외부에 있는 타사로 전송"* 이고,
  광고 ID 는 구글 광고 네트워크로 나감
- **UMP 동의 양식이 존재한다는 것 자체가 근거** — 단순 위탁 처리라면 이용자
  동의를 받을 이유가 없음
- 과다신고는 보수적, 과소신고는 정책 위반

**질문:** 구글의 "서비스 제공업체(service provider)" 예외가 AdMob 에 적용되나요?
즉 AdMob 으로 광고 ID 를 보내는 것을 "공유" 가 아니라 "수집" 으로만 신고하는
것이 맞는 사례가 있나요?

**참고:** 자체 Firebase RTDB 로 가는 1v1 플레이어 ID 는 "공유" 에 넣지
않았습니다(개발자 소유 인프라 = 위탁). 이 구분이 맞나요?

## §2. 출시 경로 — 판단을 검토받고 싶은 것

### 2-1. 공개 테스트를 한 단계 거치는 것이 맞나

**현재 계획:** 프로덕션 직행 대신 공개 테스트(오픈 베타) → 관찰 → 프로덕션
단계적 출시(5% → 20% → 50% → 100%).

**내 근거:** 실제 광고 단위를 처음 켜는 빌드이고, 무효 트래픽이나 정책 문제가
나오면 그 이력이 프로덕션 트랙에 남지 않는 편이 낫다.

**질문:** 이 판단에 반대할 이유가 있나요? 예를 들어

- 공개 테스트 단계가 스토어 노출·순위에 불리하게 작용하나요?
- "얼리 액세스" 표시가 초기 리뷰·설치에 실제로 얼마나 영향을 주나요?
- 공개 테스트에서 프로덕션으로 승격할 때 리뷰·설치수·평점이 승계되나요?

**첫 출시라 되돌릴 수 없는 선택을 피하려는 것이 목적입니다.**

### 2-2. `app-ads.txt` 없이 출시해도 되나

**현재 판단:** 없으면 일부 프로그래매틱 수요가 빠져 수익이 줄지만 출시를 막지는
않는다. 스토어 리스팅이 생겨야 크롤러가 개발자 웹사이트를 찾아갈 수 있으므로,
공개 테스트 출시 → 그다음 게시.

**질문:** 순서가 맞나요? 리스팅 없이 미리 올려둘 방법이 있나요? 없을 때 수익
손실이 실제로 어느 정도인가요(대략적인 감이라도)?

### 2-3. 프로덕션 액세스가 거절될 경우 재신청 규칙

**모릅니다.** 승인은 이미 받았으므로 지금은 해당 없지만, 향후 다른 앱을 위해

## §6. 그 밖에 봐주면 좋을 것

특별히 의심하는 것은 없지만 **다른 눈이 보면 다르게 보일 수 있는** 곳입니다.

```
src/ads/adMobProvider.js       동의 흐름과 canRequestAds 사용
src/firebase/battleService.js  1v1 매칭 경합 처리 (동시 검색 시 호스트 결정)
scripts/lib/locales.js         로케일 단일 출처 + 두 목록 교차 검증
docs/RELEASE_STATE.md          콘솔 신고 이력 — 사실과 다른 것이 있나
```

**`docs/RELEASE_STATE.md` 가 특히 중요합니다.** 콘솔 설정은 코드에 흔적을 남기지
않아 어떤 게이트도 검증할 수 없고, 그 파일이 유일한 기록입니다. 사용자가 콘솔
화면을 보여줄 수 있으니 **적힌 것과 실제가 다른 곳**을 찾아주시면 가장 값집니다.

### 5-1. 테스터 피드백: "게임 후 결과 표시가 진행도인지 뭔지 알 수 없다"의 실체 규명!

```jsx
<div className="comp-row">
  <div className="comp-player-info">
    <span className="comp-name">{t('battleResult.you')}</span>
    <span className="comp-hearts">❤️ 3</span>
  </div>

</div>
```
* **문제점**:
  * 유저 이름과 하트 옆에 달랑 **`75%`**, **`52%`**라는 숫자 배지만 덩그러니 붙어 있습니다.
  * 이 숫자가 **"퍼즐 완성도(진행률)"**인지, **"내 정답 정확도(Accuracy)"**인지, 아니면 **"승률(Win Rate)"**인지 설명해 주는 **라벨(헤더)이 화면 어디에도 없습니다.**
  * 배틀 도중 상대가 3실수로 실격해서 내가 52%만 풀고 이겼을 때, 결과창에 `52%`가 찍혀 있으면 테스터 입장에서는 *"내가 52%밖에 못 맞췄다는 건가? 이게 뭐지?"* 하고 혼란스러울 수밖에 없습니다.
* **해결 방안 (향후 작업 시)**:
  * 비교 카드 상단에 작은 라벨로 `t('battleResult.progressLabel')` (예: "퍼즐 완성도 / Puzzle Progress")를 한 줄 표기해주면 테스터의 의문이 100% 해소됩니다.

Firebase RTDB가 개발자 지시에 따라 처리하는 범위에는 서비스 제공업체 예외를 적용할 근거가 있습니다. **개발자 계정으로 만든 인프라라는 이유만으로 모든 전송이 예외가 되지는 않습니다.** 다른 이용자에게 전달하는 대전 정보와 별도 서비스의 처리도 각각 봐야 합니다. Firebase는 일반적으로 Google이 처리자·서비스 제공업체 역할을 한다고 설명합니다. [Firebase 개인정보 처리 역할](https://firebase.google.com/support/privacy)

[데이터 종류 정의](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en-GB), [SDK의 처리 내용](https://developers.google.com/admob/android/privacy/play-data-disclosure)

**§2-1. 공개 테스트 — 선택에는 동의, 정책 위험 격리라는 근거에는 반대**

[첫 출시 제한](https://support.google.com/googleplay/android-developer/answer/9859348?hl=en), [단계적 출시는 업데이트에 적용](https://support.google.com/googleplay/android-developer/answer/6346149?hl=en)

**§2-2. app-ads.txt — 출시 전에 게시 가능하며, 새 AdMob 앱 검증과 연결됨**

‘웹사이트에 파일을 게시하는 시점’과 ‘AdMob이 공개 스토어를 통해 파일을 찾아 검증하는 시점’을 구분해야 합니다. 파일은 출시 전에 개발자 사이트 루트에 올릴 수 있습니다. **‘무조건 출시부터 해야 한다’는 답은 틀렸습니다.** AdMob에 미출시 앱을 등록하는 것도 가능합니다. [파일 설정](https://support.google.com/admob/answer/9363762?hl=en), [AdMob 앱 등록](https://support.google.com/admob/answer/9989980?hl=en-GB)

2025년 1월부터 AdMob에 새로 설정하는 앱은 app-ads.txt를 통한 앱 검증이 필요합니다. 검증 및 앱 준비 상태 승인이 완료되기 전에는 광고를 완전히 게재할 수 없습니다. [app-ads.txt로 앱 검증](https://support.google.com/admob/answer/14538460?hl=en), [앱 준비 상태](https://support.google.com/admob/answer/10564477?hl=en)

출시 기록에는 개발자 웹사이트 칸을 비워 두었다고 적혀 있습니다. 파일 게시 외에 **스토어 등록정보의 개발자 웹사이트 연결**도 준비해야 합니다. 공개 테스트가 실제로 접근 가능한 공개 스토어 URL을 제공하고 AdMob에서 연결되는지는 그때 확인해야 합니다. 트랙 이름만으로 검증 승인을 보장할 수는 없습니다.

Gemini의 ‘eCPM 60~80% 감소’, ‘손실은 몇백 원’, ‘24~48시간 내 정상 승인’은 판단 근거로 쓰지 않는 것이 맞습니다. 앞의 두 수치는 요청량·국가·광고 형식·충전율 등의 자료 없이 계산할 수 없습니다. 크롤링과 앱 준비 상태 심사도 서로 다른 절차이며, Google은 심사가 보통 2~3일 걸리지만 더 오래 걸릴 수 있다고 설명합니다. **§3. 번역 — 자연스러움보다 먼저 고쳐야 할 정확성 문제가 있음**

대만수독협회가 사용하는 방향은 `直行、橫列`입니다. 그 자료를 용어 기준으로 삼겠다면 가로줄에 `列`, 세로줄에 `行`을 일관되게 적용하는 지적은 근거가 있습니다. 다만 이것으로 모든 대만 문맥에서 다른 용례가 불가능하다거나 `顯性數對` 등 모든 용어가 협회 표준임을 증명한 것은 아닙니다. 실제 퍼즐의 좌표 방향과 문장을 함께 대조해야 합니다. [대만수독협회 풀이 안내](https://www.sudoku.org.tw/sumain.htm)

원문의 naked pair 예시는 ‘두 칸의 후보가 각각 정확히 {3,8}뿐’인지 드러내면 더 정확합니다. 예를 들어 가로줄을 설명한다면 `同一列中，兩個格子的候選數都只有 3 和 8，因此可刪除這一列其他格子的候選數 3、8。`처럼 쓸 수 있습니다. 이것은 제가 제안하는 설명이며 원어민 최종 감수 완료 문구는 아닙니다.

## 기전이 지적과 달랐던 것 — 그래서 첫 수정이 부족했다

**1v1 3자 경합.** 지적은 "B 와 C 가 둘 다 A 를 상대로 정한다" 였다. 그래서
상대 티켓을 원자적으로 선점하게 고쳤는데, **테스트가 그 상태에서도 유령을
재현했다.**

실제 기전은 이랬다: B 는 A 의 티켓을 가져와 호스트가 되고, 같은 순간
**C 는 B 의 티켓을 가져온다.** C 의 선점은 부정하지 않다 — B 의 티켓이 그때까지
큐에 있었다. B 는 이미 방이 있어 C 의 `match_created` 를 버리고 C 만 유령과
남는다.

그래서 티켓 **두 장**을 가져와야 했다. 상대의 것과 **내 것.** 내 티켓은
"나는 아직 짝을 구한다" 는 공개된 약속이고, 호스트가 되는 순간 원자적으로
거둬야 한다.

**지적이 맞았지만 지적된 기전을 그대로 고쳤으면 반쪽만 고친 채 고쳤다고
적었을 것이다.** 테스트를 먼저 쓴 것이 그걸 막았다.

## 1. 판단과 검증 범위

**검사 체계를 폐기할 이유는 없다. 그러나 지금의 통과 결과를 기능·번역·보안의 완전성 증명으로 사용할 수 없다.** 단순히 검사 밖의 문제가 남는다는 뜻만이 아니다. 검사 스스로 보호한다고 설명한 범위에서도 미탐과 오탐을 재현했고, 개발 명세에는 실제 구현과 다른 내용이 남아 있다.

따라서 BACKLOG.md:262-271과 앞선 §7의 “문제가 확인된 4개를 제외한 나머지 34개는 제 일을 했다”는 결론은 유지할 수 없다. 4개를 발견했다는 사실은 나머지가 유효하다는 증거가 아니다. 아래에는 이미 고친 과거 결함과 구분하여 **현재 커밋에서 확인한 문제**를 적는다.

검토 방법은 현재 QA 명령·검사 코드·변이 선언·실제 구현·현행 지침의 대조, 기존 검사 실행, 원본을 바꾸지 않는 메모리 변형 및 폐기 가능한 Git fixture, 공식 문서 확인이다. 주로 QA 실행 경로의 검사와 공통 l10n 엔진, 검사기 자체, AGENTS 2개, 기술 명세 2개, BACKLOG의 검사 현황, RELEASE_STATE 및 스토어 정책 플레이북을 검토했다. 저장소 전체 파일·역사 문서 전부를 정독했다는 주장은 하지 않는다. 실제 Firebase 서버의 동시 접속·Android 실기·스토어 콘솔 현재 화면·13개 언어 원어민 전수 감수는 이번 검증 범위에 포함하지 않는다.

## 2. 먼저 고쳐야 할 검사 문제

### V01. 비밀정보 검사가 스테이징된 파일의 내용을 놓친다 — 실제 검사 전체 통과 재현

대상: scripts/tests/unit/test_no_committed_secrets.js:86-90, 100-125, 129-145.

스테이징 영역은 파일명만 검사한다. 내용 검사는 작업 폴더의 추적 파일과 커밋 이력에 수행하며, index의 내용에는 수행하지 않는다. git fsck의 unreachable 검사도 이 빈틈을 메우지 못한다. Git은 기본적으로 index의 객체를 도달 가능성 기준에 포함하기 때문이다. [Git fsck 공식 문서](https://git-scm.com/docs/git-fsck)

폐기 가능한 빈 Git 저장소에서 다음 순서로 **실제 검사 파일 전체**를 실행했다.

1. 평범한 이름 build-config.txt에 진짜 자격증명이 아닌 테스트용 비밀번호 형태를 넣고 git add.
2. 스테이징 내용은 그대로 두고 작업 폴더의 같은 파일만 안전한 텍스트로 변경.
3. 원래 test_no_committed_secrets.js 실행.

결과: stagedBaitPresent=true, workingBaitPresent=false, gateExit=0, “Repository Clean” 출력. 임시 저장소는 검증 후 제거했고, Suidoku에 비밀값을 넣거나 커밋하지 않았다.

추가 한계도 있다. CONTENT_EXCLUSIONS는 같은 줄에 process.env 같은 문자열이 있으면 그 줄의 다른 리터럴까지 면제한다. fsck 실행 실패 여부를 확인하지 않고, 읽지 못한 객체도 무시한다. 탐지 규칙 3개를 통과한 것이 모든 종류의 비밀정보 부재를 뜻하지도 않는다.

**권고:** index를 git grep --cached 또는 staged blob별로 별도 검사하고, 도구 실행 실패를 ERROR로 분리한다. 실제 자격증명을 로그에 그대로 출력하지 않으며, 광범위한 줄 단위 예외를 좁혀야 한다. 이번 결과는 현재 저장소에서 실제 비밀정보 유출을 새로 발견했다는 뜻은 아니다.

### V02. “유일해” 검사에 다중해 퍼즐을 넣어도 통과한다 — 실제 검사 전체 통과 재현

대상: scripts/tests/unit/test_sudoku_math_engine.js:43-58.

생성된 퍼즐을 풀 수 있고 그 결과가 제공된 해답과 일치하는지 검사하지만, 이 구간에서 해의 개수를 세지 않는다. 생성기만 메모리에서 “빈 81칸 + 기존 솔버가 그 빈판을 풀어 만든 한 해답”으로 대체하여 원래 게이트를 실행했다. countSolutions(board, 2)는 2인데 게이트는 유일해 관련 성공 문구와 최종 PASS를 출력했다.

빈판에 해답 하나를 제공했다고 유일해가 되지는 않는다. 현재 앱 생성기가 실제로 빈판을 출하한다는 뜻도 아니다. **검사의 유일해 보장 주장이 반례에 의해 깨졌다는 뜻**이다. 실제 생성기에는 countSolutions로 제거를 되돌리는 방어가 존재한다(src/engine/SudokuEngine.js:164-168).

2-2의 별도 시드 표본 검사가 일부 보완하지만, 동일한 생산 코드의 해 개수 계산기를 신뢰하는 한 독립적인 정답 기준은 아니다. 또한 2-1·2-2 manifest의 함수 export 이름 변경은 import 파손을 검출하는 것이며, 유일성이나 결정성을 깨뜨린 행동 변형과 같지 않다.

**권고:** 무해·유일해·다중해의 알려진 fixture, 독립 해 개수 확인, 생성 퍼즐의 단서 보존 및 해답 정합성, 서로 다른 입력 범위의 재현 가능한 시드 표본을 묶는다. import 실패는 별도 계약 검사로 분류한다.

### V03. Firebase 선점에는 새 경합 결함이 남아 있는데 매칭 검사가 그 경로를 실행하지 않는다

대상: src/firebase/transport/firebaseTransport.js:140-158, scripts/tests/unit/test_battle_matchmaking.js.

실제 claimTicket 메서드에 SDK 계약에 맞춰 다음 재시도 순서를 제공했다.

- 첫 update 호출은 티켓 객체를 받는다. seen에 저장하고 null을 반환한다.
- 다른 클라이언트가 먼저 제거한 상황을 나타내는 재시도 호출은 null을 받는다.
- 코드가 seen을 비우지 않고 null을 다시 반환한다.
- committed=true로 완료되면 마지막에 **처음 보았던 티켓**을 성공 결과로 반환한다.

Firebase transaction의 갱신 함수는 충돌 시 다시 호출될 수 있다. 따라서 첫 호출에서 보았던 값을 마지막 성공의 증거로 보관하면 안 된다. [Firebase 트랜잭션 설명](https://firebase.google.com/docs/database/web/read-and-write#save_data_as_transactions)

이는 **실제 메서드 + SDK 계약 모형 재현**이며, 운영 서버에서 동일 경합을 직접 일으켰다는 뜻은 아니다. 동시에 실제 2-9 게이트에 FirebaseTransport 메서드 호출 계측을 넣었을 때 게이트는 통과했고 Firebase 호출은 0회였다. 로컬 경로의 성공만으로 Firebase 원자성이 입증되지는 않는다.

**권고:** 티켓이 없어진 재시도에서는 선점 실패가 확정되도록 중단·상태 초기화 계약을 고치고, Firebase Emulator에서 여러 클라이언트의 재시도·인증·권한 거부·연결 종료까지 검증해야 한다. null과 transaction 중단을 뜻하는 undefined를 혼동하지 않아야 한다.

## 3. UI 검사의 통과가 실제 화면 검증을 뜻하지 않는 경우

### V04. 화면 진입 실패를 삼키고 다른 화면을 검사한다 — 브라우저 재현

대상: scripts/tests/ui/check_ui_overflow.js:98-119, 200-209.

메모리에서 로그만 추가하고 영어·이탈리아어 두 언어를 실행했다. 총 14개 화면 명목의 검사 중 다음 5개는 목표 화면으로 가지 못하고 홈을 검사했다.

- 영어: AI Battle, Daily Challenge.
- 이탈리아어: Settings, AI Battle, Daily Challenge.

클릭 예외를 catch에서 무시하며 목표 화면이 열렸는지 단언하지 않는 것이 원인이다. 실제 heading을 함께 읽어 홈에 머무는 것을 확인했다. 그래도 결과는 Layout Violations: 0, PERFECT, 종료 코드 0이었다. 전체 13언어의 방문 실패 횟수까지 측정했다는 뜻은 아니다.

또한 totalScanned += 35는 실제 요소 수를 센 값이 아니다. 13×7×35=3,185를 “검사한 요소 수”로 출력한다. overflow:hidden/ellipsis 요소는 제외하고, 자연스러운 줄바꿈도 innerText의 줄바꿈 문자만으로 모두 포착할 수 없다.

**권고:** 각 목표 화면에 독립적인 도착 조건을 두고 실패를 NOT_OBSERVED로 기록한다. 실제 조회·가시 요소 수를 집계하며, 생략 표시를 허용할 곳과 정보 손실을 금지할 곳을 구분한다. 방문하지 않은 화면을 통과로 세지 않는다.

### V05. 홈 레이아웃 검사는 주로 스크린샷 생성기다

대상: scripts/tests/ui/test_home_layout.js:90-125 및 mutations/3-5_home_layout_grid_respo.json.

탭과 버튼을 누르고 스크린샷 5장을 저장하지만, 간격·겹침·그리드·잘림·PB 표시값을 검증하는 assertion이나 이미지 기준 비교가 없다. 성공 문구도 “All screenshots captured successfully”다. 화면 촬영 도구로는 유용하지만 자동 레이아웃 품질 판정기로 부르는 것은 과장이다.

현재 변이는 export 이름을 깨뜨리고 일반적인 Error를 기대한다. 이는 레이아웃이 틀린 상태를 만들어 잡는 검증과 다르다.

**권고:** 이름을 촬영 도구로 정정하거나 실제 DOM 기하·표시값 검사와 검토된 스크린샷 비교를 추가한다. 정상적으로 렌더링되면서 카드가 겹치는 변형이 검출되어야 한다.

### V06. 색상 거리 30은 가독성 대비 기준이 아니다 — 계산 재현

대상: scripts/tests/ui/test_theme_and_button_contrast.js:142-158, 226-231, 270-275.

현재 RGB 유클리드 거리가 30보다 크면 통과한다. 실제 함수에 흰 글자 #ffffff와 배경 #e6e6e6을 넣으면 거리 43.301로 통과하지만, 상대 휘도 대비는 약 1.248:1이다. W3C 기준은 일반 텍스트 4.5:1, 큰 텍스트 3:1이다. [WCAG 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

이 계산은 현재 앱의 해당 버튼 색이 반드시 위 예시라는 뜻이 아니다. **검사 기준 자체가 낮은 대비를 통과시킨다는 반례**다. 그라디언트도 정지점만 확인하면 중간색, 투명도, 실제 글자 뒤의 배경을 놓칠 수 있다.

**권고:** 검사 목적이 단순 동일색 회귀 방지인지 접근성 대비 보장인지 명확히 하고, 후자라면 실제 합성 배경과 상대 휘도에 기반한 검사로 교체한다.


## 4. 번역·정적 검사·변이 감사기 자체의 문제

### V07. 새 CJK “전수” 검사도 기존 도해의 잘못된 한자를 놓친다 — 실제 게이트 2개 통과 재현

대상: scripts/tests/fixtures/build_han_inventory.js:93-97, 119-143,
scripts/tests/unit/test_cjk_script_purity.js, test_academy_l10n.js.

아카데미 문자열 수집 정규식은 콜론 주변 공백이 없는 "ja":"..." 형태를 전제로 한다. 기존 stage1Diagrams.js의 "ja": "..." 형태는 빠진다. 실제 full-house.label.ja의 確定를 메모리에서 确定로 바꾸고, 해당 데이터 객체와 파일 읽기 결과를 함께 바꿔 원래 게이트들을 실행했다.

결과: 인벤토리에서 确는 0→0, 게이트 2-19와 2-16 모두 PASS. 현재 데이터의 중요한 형식이 수집되지 않는 문제이므로 “드문 미래 문법은 감수한다”는 설명으로 넘길 수 없다.

observedPairs에도 별개 문제가 있다. 같은 길이의 간체·번체 문자열을 위치별로 비교하여 두 번 관찰되면 글자 대응쌍으로 승격한다. 임의 문자열 甲乙 / 丙丁를 두 번 넣었더니 甲↔丙, 乙↔丁가 채택됐다. 길이·위치·반복만으로 간체/번체 대응 관계가 증명되지는 않는다. 주석의 “한 자리만 다를 때”와 달리 여러 위치가 달라도 수집한다.

**권고:** 실제 export 객체를 읽는 동일 수집기를 사용하고, 원문 문법·따옴표·공백·escape 변경으로 수집 결과가 달라지지 않는지 검사한다. 사용 문자 snapshot은 변경 감지 장치로 유지할 수 있지만 언어학적 정답표로 부르면 안 된다. 재생성만으로 승인되는 기준선과 독립적인 단어·표기 근거를 분리한다.

현재 문자열을 실제 객체의 문자열 말단으로 세면 UI는 언어당 444개, 아카데미는 380개다. 아카데미는 32전략×3 + 64미션×2 + 156도해 블록으로 구성된다. 따라서 이 두 범위의 13언어 합계는 **5,772 + 4,940 = 10,712개 문자열 셀**이다. 같은 문구가 여러 키에 있으면 각각 세며, 스토어 문안은 포함하지 않는다.

### D01. 기술 명세의 알고리즘 설명이 현재 구현과 다르다

### D02. “전체 플레이어 상위 % / 멘사급”은 자연스러움 문제가 아니라 의미상 근거 부족이다

### D03. 공통 명세의 저장소 암호화·Zero-PII 설명은 구현과 구분해야 한다

대상: app_common/docs/COMMON_APP_TECHNICAL_SPEC.md:64-70.

“localStorage / IndexedDB에 안전하게 암호화 격리 저장”이라고 하지만, 게임과 지갑 저장은 JSON.stringify 결과를 localStorage에 쓴다(src/utils/storage.js:13,75,140; wallet.js:79). 이 경로에서 앱 수준의 암호화는 확인되지 않는다. OS의 앱 격리·기기 저장장치 암호화 가능성과 앱이 데이터를 암호화하여 저장하는 구현은 다른 주장이다.

## 6. 앞선 §7~§10 질문에 대한 답

### §7. 검사들이 전부 무효인가?

아니다. 실제 production 함수를 실행하고, 입력·출력·부수효과·순서를 검증하는 회귀 검사는 가치가 있다. 예를 들어 광고 수명주기 2-20은 응답 시점을 제어하고 정상 표시 대조군도 둔다. Device harness 2-12도 정상 행동과 알려진 잘못된 ADB 응답을 함께 검사한다. gameplay E2E의 빠른 탭 중 타이머 전진, 저장 해답 누락 후 입력, 마지막 정답 후 승리·이동 검사는 실제 사용자 행동을 확인한다.

다만 “이 테스트는 가치가 있다”와 “머리말의 모든 보장을 입증한다”는 별도 판단이다. 새로운 결함이 확인된 검사는 이름·설명·판정·입력을 함께 고쳐야 한다. 현재 구조에서는 잘못된 요약뿐 아니라 실제 assertion 누락과 parser 오류도 원인이다.

### §8~§9. 번역 의미는 검증할 수 없는가? LLM 교차검토를 게이트로 써도 되는가?

**모든 자연어 의미를 결정론적으로 증명할 수 없다는 것과 의미상 일부 계약을 검사할 수 없다는 것은 다르다.** 아카데미 지시의 대상 칸·숫자, 보상 개수, 부활 후 실수, 업적 달성 조건 등은 구조화된 원천 데이터와 문구를 연결하여 검증할 수 있다. 이번 “전체 플레이어 백분위” 사례는 번역 이전의 원문 의미 검토로 찾았다.

우선순위는 금전·개인정보·동의·패배/부활·보상·풀이 지시처럼 오해의 비용이 큰 문구다. 해당 문구의 원천 사실, 각 언어의 번역, 실제 표시 위치를 함께 검토한다. 단순히 모든 문구를 짧게 만들거나 부정 문자 목록을 늘리는 것은 의미 검증이 아니다.

LLM 교차검토는 **의심 항목을 찾는 보조 검토**로 유용하다. 먼저 사람이 판정한 정상/오류 표본으로 평가하고, 출처 문구·키·언어·위치·문제 근거를 출력하게 해야 한다. 여러 모델이 동의했다는 사실만으로 원어민 검증과 동등해지지 않는다. 합의 여부로 즉시 자동 수정하거나 불안정한 판정을 곧바로 릴리즈 차단 기준으로 삼지 않는다. 확정된 오류는 재현 가능한 fixture로 승격할 수 있다.

21개 일본어 문자 치환도 단일 문자 대응표만으로 모든 단어의 타당성을 승인할 수 없다. “현재 인벤토리에 있다”, “간체/번체에서 같은 위치였다”는 근거는 일본어 단어의 정당성 증명이 아니다. 이미 수집기 누락이 있으므로 “이제 남은 것은 자연스러움뿐”이라는 §9-3의 결론도 성립하지 않는다. 모든 일본어 문장과 21개 치환의 모든 용례를 이번 감사에서 전수 감수했다고 주장하지 않는다.

Gate 5에 CJK 용어 규칙이 부족한 문제와 문자 수집 누락은 구분해야 한다. 플랫폼 용어 검사를 문자 순도 검사의 대체물로 키울 필요는 없다. 먼저 입력 수집을 바로잡고, 각 게이트가 책임지는 명제를 명시하는 것이 순서다.

### §10. 문서 외에 무엇이 반복을 막는가? 89개면 충분한가?

문서의 경고를 더 늘리는 것보다 **관찰 실패가 통과로 변환될 수 없는 실행 계약**이 필요하다.

1. 각 검사에 요구사항·검사 대상·입력 범위·정답 기준·실제 수행 조건을 연결한다.
2. 결과는 PASS / FAIL / ERROR / NOT_OBSERVED로 구분한다. 필수 항목의 미관찰은 전체 성공에 합산하지 않는다.
3. 파서·로케일 목록·환경 읽기·프로세스 실행기를 공유하고 그 자체를 정상/오류/문법 동치 fixture로 검사한다.
4. 동일 의미의 공백·따옴표·주석·개행 변경은 같은 판정을 내야 한다. 잘못된 호출 옆에 정상 호출을 추가해도 잘못된 호출 검출이 사라지면 안 된다.
5. 변이는 문법적으로 유효하고 실제 기능 경로에 도달한 뒤 예상 결함을 만드는지 확인한다. 단순 import 파손과 제품 행동 파손을 별도로 집계한다.
6. 최종 보고는 집계 숫자를 다시 손으로 작성하지 말고 구조화된 실행 결과에서 만든다. 모델·검토자는 그 결과의 범위를 설명한다.
7. 외부 정책은 출처·확인 날짜·해당 계정 조건을 붙이고, 회고에서 얻은 경험을 자동으로 공통 금지 규칙으로 승격하지 않는다.

**89라는 총수나 게이트당 평균 2.3으로 충분성을 판단할 수 없다.** 이번 반례들이 이미 부족한 영역을 특정한다.

| 먼저 보강할 영역 | 필요한 변형·대조군 |
|---|---|
| 비밀정보 검사 | index만 오염, 작업 폴더만 오염, scanner 오류, 예외 문자열과 실제 리터럴 동거 |
| 퍼즐 엔진 | 다중해·무해·단서와 불일치하는 해답·잘못된 해 개수 함수·시드와 무관한 상수 생성기 |
| Firebase 대전 | transaction 재시도, 3명 이상 동시 진입, 권한 거부, 연결 종료, 같은 승패 이벤트 재전송 |
| UI 방문·배치·대비 | 목표 요소 삭제, 라우트 오연결, 렌더링은 성공하지만 겹치는 배치, 낮은 휘도 대비, 미지원 언어 선택자 |

## 7. 후속 수정 순서와 완료 판정

우선 비밀정보 index 누락, Firebase 선점 재시도, CJK 수집 누락, UI 방문 실패 은폐를 수정하는 것이 좋다. 그 다음 변이 실행기의 결과 분류·격리, 독립적인 퍼즐 기준, 정적 parser를 보강한다. 동시에 명세의 구현 사실·IQ/백분위 문구·스토어 정책 오답을 정정한다. 파일 길이와 색상 거리 같은 팀 선택은 목적을 좁혀 설명한다.

**완료의 조건은 새 게이트 수 증가가 아니라 이번 반례가 해당 이유로 실패하고 정상 대조군이 계속 통과하는 것**이다. 여기 적힌 모든 문제를 곧바로 새 파일·새 게이트 하나씩으로 만들 필요는 없다. 기존 검사에 통합하고 공통 수집·판정기를 고치는 편이 관리하기 쉽다.

[티켓, null]  → 거부해야 함  ❌ 선점했다   ← 감사가 말한 그대로

기전도 감사가 맞다. `return current`(=null)는 **중단이 아니라 "지워라" 라는 쓰기**라
committed=true 가 되고, 클로저의 `seen` 에 1회차 티켓이 남아 성공으로 반환된다.

경로에 로그를 넣었다.

```
[B] update fn called with: null
[B] update fn called with: null      ← 티켓을 한 번도 못 봤다
```

**`null` 이 두 가지를 뜻한다.** 로컬 캐시가 비어 있으면 Firebase 는 **첫 호출을
null 로 시작한다.** 그 null 은 "남이 가져갔다" 가 아니라 "아직 안 받았다" 이고,
원래 코드의 `return current` 가 **서버 왕복을 부르는 동작**이었다. 감사가
*"null 과 transaction 중단을 뜻하는 undefined 를 혼동하지 않아야 한다"* 고 적은
바로 그 구분이, 반대 방향으로도 필요하다.

**수정:** 두 null 을 **"이 트랜잭션 안에서 티켓을 본 적이 있는가"** 로 가른다.
본 적 없이 온 null → `return current`(왕복 유도). 본 뒤에 온 null → `undefined`(중단).

**재실행:** 3-10 exit 0(실매칭 복구), `[티켓, null]` 은 여전히 거부.

## 2. 감사에 없던 것 (재현 과정에서 나옴)

### N-1. 게이트 3-1 의 판정이 체크아웃 설정에 의존한다

주석 제거 정규식의 `.*$` 가 **`\r` 를 넘지 못한다**(`.` 는 줄 종결자를 제외).
**CRLF 파일에서는 줄 끝 주석이 한 줄도 안 걷힌다.**

이 저장소는 `core.autocrlf = true` 다 — git 은 LF 로 보관, 작업 폴더는 CRLF.
**HEAD 내용을 그대로 CRLF 로 먹이면 내 수정과 무관하게 위반 2건이 나온다.**
같은 커밋이 기계에 따라 통과하기도 실패하기도 하며 `git diff` 에는 아무것도
보이지 않는다. 기존 expectSurvival 대조군이 통과하던 이유는 그 변형의 대상 파일이
마침 LF 였기 때문이다.

이것은 감사 §6-10 의 4번 — *"동일 의미의 공백·따옴표·주석·개행 변경은 같은
판정을 내야 한다"* — 의 실례다.

**수정:** 줄마다 `\r` 를 먼저 제거. **확인:** 그 한 줄을 빼고 변형 감사를 돌리면
**BASELINE_RED**(변이 전에 이미 빨감). LF 체크아웃에서도 잡히도록 명시적 `\r` 를
넣는 expectSurvival 변형 추가.

### N-2. 변형 실행기가 여러 줄 앵커를 CRLF 에서 못 찾는다

기준 실행의 ANCHOR_MISSING 2건은 **내 작업과 무관한 기존 부식**이었다.

```
2-14  versionName "1.2.3"      1.2.5 로 올렸는데 앵커 미갱신 (e92d9fa)
2-16  zh-TW 줄 전체 (\n 포함)   매니페스트는 \n, 작업 폴더는 CRLF → 영영 불일치
```

후자는 **매니페스트가 옳았다.** `original.split(mut.find)` 가 문자열 그대로 비교하므로
**이 저장소에서 줄을 넘는 앵커는 전부 태어날 때부터 죽어 있었다.**

**수정:** 실행기가 파일 자신의 줄 종결자로 맞추게 함. 2-14 앵커 재지정.
전 매니페스트 앵커 90개 훑어 **미해결 0** 확인.

### N-3. 2-9 변형 하나가 간헐적이다 — **미해결**

전체 감사 2회의 결과가 달랐고, 그 사이 변경분은 2-9 가 import 하지 않는 파일뿐이다.

### 숨은 쌍·트리플·쿼드 연습 6개: 후보 축소와 숫자 확정을 혼동

현재 데이터의 부분집합 후보를 남기고 서로 다른 숫자의 가능한 배치를 메모리에서 열거했다. 해당 기법만 적용하면 아래처럼 **목표 칸 후보가 여러 개 남는다**. 전체 9×9 퍼즐의 해답 수를 센 결과가 아니라, 화면에 제시한 기법으로 얻을 수 있는 결론을 검증한 결과다.

| 연습 ID | guide 위치 (`src/data/academy/practice/`) | 일본어가 입력하라고 하는 숫자 | 기법 적용 후 목표 후보 | 해당 부분집합의 가능한 배치 수 |
|---|---|---|---|---|
| `hidden_pair_ex1` | `stage2PairsPractice.js:31` | `3` | `{3,8}` | 2 |
| `hidden_pair_ex2` | `stage2PairsPractice.js:40` | `6` | `{6,9}` | 2 |
| `hidden_triple_ex1` | `stage2TuplesPractice.js:31` | `8` | `{5,8}` | 3 |
| `hidden_triple_ex2` | `stage2TuplesPractice.js:40` | `9` | `{3,9}` | 2 |
| `hidden_quad_ex1` | `stage2TuplesPractice.js:71` | `1` | `{1,4,9}` | 8 |
| `hidden_quad_ex2` | `stage2TuplesPractice.js:80` | `4` | `{2,4,8}` | 4 |

예를 들어 `hidden_pair_ex1.guide.ja`는 `余分な候補が消去され [3] が確定しました。3 を入力してください。`라고 하지만, 목표 칸에 8을 두고 다른 쌍 칸에 3을 두는 배치도 남는다. 올바른 원리 설명은 다음과 같다.

> この行で 3 と 8 が入るのは、この2マスだけです。この2マスから 3 と 8 以外の候補を消去できますが、どちらのマスが 3 になるかは、まだ確定しません。

이 설명만 교체하면 현재 ‘정답 하나 입력’ UI와 충돌한다. 후보를 지우는 연습으로 바꾸거나, 한 숫자로 확정되는 추가 근거를 보드와 설명에 함께 제공해야 한다. 현재 입력 성공은 `useInteractivePractice.js`에서 저장된 `correctVal`과 같은지 비교한 결과이므로 풀이 증명이 아니다. [HoDoKu Hidden Subsets](https://hodoku.sourceforge.net/en/tech_hidden.php)도 숨은 쌍이 두 숫자의 자리를 개별적으로 결정하는 것은 아니라고 설명한다.

## 3. 상급 기법의 의미 누락과 설명 조건

### 3-1. 일본어에서 추가로 달라진 의미

**UR의 직사각형 조건 누락 — `src/data/academy/stage4.js:23`, `unique-rectangles.desc.ja`.** 한국어·영어의 직사각형 조건이 일본어에서는 `2つのブロックに跨る4マス`만 남았다. 임의의 네 칸에 적용할 수 없다. 다음처럼 범위와 유일해 전제를 보강한다.

> 解が1つに定まる問題では、2行・2列・2ブロックにまたがる長方形の4マスが、同じ2候補だけになる配置は成立しません。追加候補のあるマスに着目して、候補を絞り込みます。

이는 UR의 개요 문구이며 유형별 실제 소거 조건을 대신하지 않는다. [HoDoKu Uniqueness](https://hodoku.sourceforge.net/en/tech_ur.php)

**Exocet의 Target/Companion 혼동 — `src/data/academy/practice/stage5Practice.js:91`, `exocet_ex1.guide.ja`.** 일본어는 `Baseセル [1,2] と [3,4] … Targetセルで正解 [5] が確定`이라고 한다. 영어·한국어는 companion을 명시한다. 표준 Junior Exocet의 Target에는 base 숫자가 들어가므로, 이 사례에서 5를 Target의 정답이라고 하는 설명은 반대 방향이다. [SudokuWiki Exocet의 Elimination Rule 1](https://www.sudokuwiki.org/exocet?talk=)

그러나 단어만 `コンパニオンマス`로 바꿔서는 해결되지 않는다. 실제 축약 보드에는 Cross-Line·Target·Companion 관계를 증명할 정보가 없다. 렌더러의 `type: target`은 일반적인 입력 대상이라는 뜻이며, Exocet의 기술적 Target이라는 보증이 아니다. **예제 구조를 먼저 검증한 뒤 일본어를 맞춰야 하며, 현재 데이터에서 5가 논리적으로 증명됐다는 교정 문장을 새로 만들지 않는다.**

- 위 임시 브라우저는 외부 통신을 차단했다. 실제 구매·계정 동기화·온라인 매칭을 실행하지 않았다. 사용자의 실제 앱 데이터 대신 임시 브라우저 저장소를 사용했다.
- 재개 후 `test_academy_l10n.js`, `test_cjk_script_purity.js` 재실행 통과. 최종 일본어 한자는 **497종**, 목록 밖 0종이다. 전날의 496종에서 바뀐 것은 추가 문구 때문이다. 새로 확인한 명백한 간체자 혼입은 없었다.
- 9/17에 실행한 `npm run qa`는 0~2단계 및 3-3까지 진행했고, 3-4의 Playwright 실행에서 `spawn EPERM`으로 중단됐다. **Oxlint는 이번에는 통과했다.** 과거 실행 환경의 오류를 현재 결과로 재사용하지 않았다. 전체 QA는 환경 `ERROR`로 미완료이며, 이 결과를 전체 통과라고 쓰지 않는다. 이번 일본어 화면 확인은 별도로 허용된 브라우저 실행에서 완료했다.

### 아직 확인하지 않은 것

Android 실기기의 시스템/광고 SDK/스토어 결제 화면, 모든 화면 크기의 줄바꿈·넘침, 모든 오류·결과 모달의 런타임 노출, 64개 연습 모두의 완전한 수학적 증명은 이번 완료 범위가 아니다. 사전 독해 완료가 모든 문자열의 실제 노출 확인을 뜻하지도 않는다. 스토어 소개 문구·이미지의 일본어는 별도 대상이다. 원어민 사용성 테스트를 했다는 주장도 하지 않는다.

`ONLINE PVP`, `VS AI`, `DAILY`, 업적 등급의 영문은 실제 화면에 있지만 영어 배지 존재 자체를 일본어 오류로 판정하지 않았다. `header.soundOn`의 `効果音OFF`도 누르면 소리를 끄는 동작을 표시하므로 키 이름과 반대라는 이유로 오역이 아니다. 실습 데이터의 `cell.title`에 있는 `Base 1` 등의 영문은 렌더러가 출력하지 않으므로 보이는 미번역으로 세지 않았다. 반면 `Stage5MiniGrids.jsx`의 HTML `title="Eliminated"`는 `除外済み`로 현지화할 수 있는 보조 문구다. 네이티브 터치 환경에서 그 툴팁이 노출되는지는 확인하지 않았다.

### Claude·Gemini와 다음 수정 때 공유할 판단

1. 먼저 명확한 문장 연결, 행·열, 후보 숫자, 제목·본문 불일치를 고친다.
