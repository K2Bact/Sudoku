## 왜 통합했나

`PROJECT_IDEAS_AND_BACKLOG.md` 의 "출시 직전 필수 게이트" 4개 중 **3개가 이미
해결됐는데도 "대기 중" 으로 적혀 있었습니다.** 코드를 직접 확인하고 알았습니다.

| 문서가 말한 것 | 실제 코드 |
|---|---|
| AdMob 테스트 ID 교체 대기 | 테스트 ID 테이블 자체가 없음. `.env` 한 줄로 전환 |
| 가상 랭커 → 실제 데이터 전환 대기 | 이미 백분위 라벨(`TOP 0.1%`)로 교체됨 |
| Play 게임즈 "나머지 안전 플레이스홀더" | 플레이스홀더 없음. 실제 ID 하나 + 정직한 no-op |

**끝난 일이 "대기 중" 으로 남아 있으면, 다음에 읽는 사람이 없는 일을 하려 듭니다.**
그래서 이 파일에는 **코드로 확인한 상태만** 적습니다. 확인하지 않은 것은 "미확인" 이라고
적습니다.

### R-3. 광고 — **SDK 통합은 끝났습니다 (2026-09-05)**

이 항목은 오래 "출시 시점에 넣을 것" 으로 적혀 있었고 **그것이 틀렸습니다.**
클로즈 테스트 중 광고가 위험하다는 이유였는데, 위험한 것은 *실제* 광고를 우리가
누르는 것(invalid traffic)이지 광고 코드의 존재가 아닙니다.

**구글이 공개한 샘플 단위 ID 는 항상 테스트 광고만 반환하고 눌러도 됩니다.**
지금 그 위에서 돌고 있습니다.

| 항목 | 상태 |
|---|---|
| `@capacitor-community/admob` 설치 + `cap sync` | ✅ |
| 배너 · 전면 · 리워드 (샘플 단위 ID) | ✅ 실기 검증 완료 |
| UMP 동의 (요청·양식·재방문 경로) | ✅ 실기 검증 완료 |
| 전면 빈도 제한 1시간 | ✅ 실기 검증 완료 |
| 정책 문서 · AD_ID 권한 · 데이터 보안 신고 | ✅ |
| **실제 광고 단위 ID 로 전환** | ✅ 2026-09-11 · 테스트 스위치는 아직 켜둠 |

**남은 것은 값 하나뿐입니다.** (2026-09-11 갱신)

```
✅ .env             VITE_ADMOB_BANNER_ID / _INTERSTITIAL_ID / _REWARDED_ID
✅ AndroidManifest  APPLICATION_ID  ca-app-pub-4962315343548854~7282504859
✅ app-ads.txt      k2bact.github.io 루트에 게시 · HTTP 200 · text/plain 확인
❌ .env             VITE_ADMOB_TESTING=false   ← 마지막 하나
```

**`VITE_ADMOB_TESTING=true` 를 일부러 켜둔 상태입니다.** 실제 단위 ID 가 들어가
있어도 이 스위치가 SDK 에 테스트 요청으로 표시하게 만듭니다. 두 신호가 다
필요하고, 하나만으로는 안전하지 않습니다.

**⚠️ `false` 로 바꾼 뒤에는 우리 기기로 광고를 누르지 마세요.** 그 시점부터
우리 클릭이 invalid traffic 이고, 그것이 AdMob 계정이 정지되는 경로입니다.
순서는 이렇습니다 — **테스트 스위치를 켠 채로 실제 ID 를 기기에서 확인하고,
그 다음에 스위치를 끄고, 그 빌드는 누르지 않습니다.**

> 상세한 현재 상태·실기 검증 이력은 `RELEASE_STATE.md`,
> 통합 방법과 함정은 `app_common/docs/COMMON_APP_TECHNICAL_SPEC.md` §5 에 있습니다.

### R-5. 인앱 결제 — 계획이 존재하지 않는 패키지를 가리키고 있었습니다 (2026-09-11 신규)

**출시된 앱은 멀쩡합니다.** `isAvailable` 이 false 라 광고 제거 화면이 아예
열리지 않고, 아무것도 팔리지 않았고, 아무도 깨진 결제를 보지 않았습니다.
결함은 **계획과 그 문서**에 있지 동작에 있지 않습니다.

#### 무엇이 잘못돼 있었나

`src/billing/index.js` 주석이 출시 절차를 이렇게 적어두고 있었습니다.

```
1. Play Console 에 상품 생성
2. npm i @capacitor-community/in-app-purchases && npx cap sync
3. VITE_BILLING_PROVIDER=play
   "Step 3 alone is the switch. No screen or service code changes."
```

**세 가지가 전부 틀렸습니다.**

**① 순서가 불가능합니다.** Play Console 은 `com.android.vending.BILLING` 권한이
든 빌드가 업로드돼 있어야 일회성 제품 생성을 열어줍니다. 권한은 결제 라이브러리가
가져오므로 **플러그인이 먼저입니다.** 상품을 먼저 만들 방법이 없습니다.

**② 그 패키지가 존재하지 않습니다.**

```
npm view @capacitor-community/in-app-purchases   →  404 Not Found
```

**③ 실존하는 대안들은 API 가 전혀 다릅니다.** `playBillingProvider.js` 는
설정만 바꾸면 켜지는 상태가 아니라 **다시 써야 하는 상태**입니다.

| 우리 코드 | `@capgo/native-purchases` 실제 |
|---|---|
| `Plugins.InAppPurchases` | `NativePurchases` |
| `initialize()` | 없음 (`isBillingSupported()`) |
| `getProducts({productIds})` → `.products[].id` | `getProducts({productIdentifiers, productType})` → `.identifier` |
| `purchase({productId})` → `.cancelled` | `purchaseProduct({productIdentifier, productType})` |
| `acknowledge({transactionId})` | 없음 — 자동 승인 |
| `getPurchases()` → `.purchases[].productId` | `getPurchases({productType})` → `.productIdentifier` |

메서드 이름·인자 이름·반환 필드·플러그인 등록 이름까지 전부 다릅니다.

#### 게이트 2-13 은 거짓말하지 않았습니다

"Billing Honesty" 는 **못 파는 것을 파는 척하지 않는가**를 검사하고, 그건 참입니다.
플러그인이 없으면 `isAvailable` 이 false 이고 화면이 안 열리는 것까지 확인합니다.

**다만 그 패키지가 실재하는지는 검사하지 않습니다.** 오늘 하루 반복된 패턴과
같습니다 — 게이트는 자기가 보는 것에 대해 맞고, 초록이 더 넓게 읽혔습니다.
이 항목은 그 초록을 "결제는 준비됐다" 로 읽은 결과입니다.

#### 무엇을 골라야 하나 — 미결

Suidoku 는 **안드로이드 전용**이고 iOS 폴더가 없습니다. 상품은 **하나**,
**영구 구매**, **구독 없음**입니다.

| 패키지 | 버전 | 성격 | 비용 |
|---|---|---|---|
| **`@capgo/native-purchases`** | 8.7.0 (2026-08-24) | Play Billing 에 직접 연결. 버전이 Capacitor 메이저를 따라가고 우리가 Capacitor 8 | 무료 |
| `@revenuecat/purchases-capacitor` | 13.5.1 | 구매 기록을 RevenueCat 서버가 관리 | 월 추적매출 $2,500 까지 무료, 초과분은 **총매출의 1%** |
| `cordova-plugin-purchase` | 13.18.0 | Cordova 계열. 널리 쓰이지만 크고 오래됨 | 무료 |

RevenueCat 이 해결하는 문제 — 구독 갱신 추적, iOS/안드로이드 구매 통합,
영수증 검증 서버 — 를 **우리는 하나도 갖고 있지 않습니다.** 그래서 지금은
`@capgo/native-purchases` 가 맞아 보이지만, **결정되지 않았습니다.**

#### 결정 후의 실제 순서

```
1. 플러그인 설치 + npx cap sync       .env 는 none 그대로
2. playBillingProvider.js 를 그 API 로 다시 작성
3. 병합된 매니페스트에 BILLING 권한이 들어갔는지 확인
4. 1.2.4 빌드 → 테스트 트랙 업로드      ← 이게 올라가야 상품을 만들 수 있음
5. Play를 통한 수익 창출 → 제품 → 일회성 제품
     ID `remove_ads_permanent` (변경 불가) · 비소비성 · 구매 옵션 + 가격 · **활성화**
6. VITE_BILLING_PROVIDER=play → 1.2.5 빌드 → 업로드
7. 라이선스 테스터 계정으로 실제 구매 검증
```

**업로드가 두 번 필요하고 순서를 바꿀 수 없습니다.** 6번을 5번보다 먼저 하면
`isAvailable` 이 플러그인 존재만 보기 때문에 화면이 열리는데 버튼에 가격이 없고
누르면 에러가 납니다.

**5번의 활성화를 빠뜨리면** 구매 옵션이 `임시` 로 남고 Play Billing Library 가
아예 반환하지 않습니다. 에러가 아니라 **상품이 없는 것처럼 보입니다** —
1.2.2 를 업로드만 하고 출시를 안 눌렀던 것과 같은 함정입니다.

#### 급하지 않습니다

광고가 이미 붙어 있고 수익 경로가 있습니다. 결제는 **광고 제거를 팔고 싶을 때**
하면 되고, 그때까지 화면은 닫혀 있는 것이 옳습니다. 서두를 이유가 없는데
서둘러서 "결제된 척" 하는 화면을 한 번 출시한 적이 있습니다.

### 왜 언어만 끝없이 문제가 나오는가 — 인상이 아니라 구조입니다

```
로케일                 13개
번역 문자열 전체        8,866   (언어당 682 = i18n 312 + 아카데미 370)
그중 읽을 사람이 있는 것   682   ← 한국어
읽을 사람이 없는 것     8,184   = 92.3%
```

**코드에는 읽는 사람이 있습니다.** 개발자가 읽고, 테스트가 실행하고, 틀리면
안 돌아갑니다. **번역에는 없습니다.** 12개 언어 8,184개 문자열은 맞는지 틀린지
판정할 수 있는 사람이 이 프로젝트에 아무도 없습니다.

그리고 결정적으로 — **기계 번역은 유창하게 틀립니다.** 코드가 틀리면 죽지만
문장은 틀려도 읽힙니다. `pointing_pairs_ex2` 의 제목이 13개 언어 전부
`[3]` 이라고 말했고 3 은 정답도 소거값도 아니었는데, **12개 언어 번역가라면
누구도 의심할 수 없습니다.** 원본이 3 이라고 적혀 있으니 3 이라고 옮깁니다.

그래서 이 영역의 모든 검사는 **대리 검사** 입니다.

```
키가 다 있는가            검사함   ← 뜻이 맞는지는 모름
토큰이 대칭인가           검사함   ← 문장이 자연스러운지는 모름
문자 체계가 섞였는가       검사함   ← 낱말 선택이 맞는지는 모름
번역이 실제로 됐는가       검사함   ← 번역이 좋은지는 모름
────────────────────────────────────
뜻이 맞는가              못 함
```

**대리 검사에는 반드시 틈이 있고, 틈의 크기를 검사 자신이 모릅니다.**
언어에서 계속 문제가 나오는 것은 검사가 부실해서가 아니라 **이 구조가 그대로이기
때문**이고, 게이트를 더 만들어도 이 성질은 사라지지 않습니다.

### C-5. 게이트가 없는 자리 — 일부러 만들지 않았습니다 (2026-09-11 신규)

이번 회차에 게이트 여섯 개를 손봤지만 **두 가지는 게이트로 만들지 않았습니다.**
빠뜨린 것이 아니라 만들지 않기로 한 것이고, 그 이유를 적어둡니다.

#### 1. 문구가 코드 조건과 맞는지

업적 `win_5` 의 조건은 `won >= 5` 인데 제목이 "5전 5승" 이었습니다. 20패 후
5승이어도 달성됩니다. en/de/fr/es 는 "High Five" 같은 말장난이라 문제가 없고,
**CJK 4개 로케일만 거짓을 말했습니다.**

이걸 기계로 잡으려면 제목의 *의미* 를 이해해야 합니다. "5전" 이 "5경기 치름" 을
뜻하고 앱이 경기 수를 업적 조건에 쓰지 않는다는 것까지 알아야 합니다.

**기계로 할 수 있는 척하는 검사를 만들면 그게 곧 장식이 됩니다.** 그리고 장식은
초록불로 사람을 안심시키므로 없는 것보다 나쁩니다. 이건 읽어서 찾았고 앞으로도
읽어서 찾아야 합니다. 그렇게 적어두는 편이 낫습니다.

**할 일:** 새 업적·새 문구를 추가할 때 제목이 코드가 검사하지 않는 조건을
주장하는지 사람이 확인합니다. 13개 언어 중 일부만 틀릴 수 있으므로
**한 언어를 보고 넘기지 마세요** — 이번에도 CJK 4개만 틀렸습니다.

#### 2. 하드코딩 스캐너에 남은 구멍 — 방향까지 적어둡니다

`check_no_hardcoded_text.js` 가 줄 끝 주석을 걷어내도록 고쳤습니다. 남는 구멍:

```js
const a = 'x//y'; const b = '안녕';   // ← 뒤쪽 한국어가 가려집니다
```

문자열 안의 콜론 없는 `//` 뒤가 주석으로 취급됩니다. 자바스크립트를 제대로
토큰화하지 않는 한 이 구멍은 남습니다.

**받아들인 이유:** `'x//y'` 형태가 이 저장소에 하나도 없다는 것을 확인했고,
반대쪽 비용이 실재했습니다. 한국어 주석 하나 때문에 게이트가 빨개지면
**게이트를 조용히 만드는 가장 쉬운 방법이 주석을 영어로 바꾸는 것**이 되고,
그러면 이 저장소에서 가장 값나가는 부분 — 왜 그렇게 고쳤는지의 기록 — 이
사라집니다.

**할 일:** 우선순위 낮음. 토큰화로 바꾸면 메워집니다. 그때까지는 위 형태를
코드에 쓰지 않습니다.

> every message here is ~100 bytes

주고받는 것은 진행률 숫자 하나이고 실시간 조작이 아닙니다. 지연이 실제로

결승 규칙으로 처리했습니다 — 네트워크 도착 순서에 기대지 않습니다.

**그래서 지역 매칭을 도입할 유인이 없습니다.**

적어두는 유일한 이유입니다.

```
1. Play Console → 데이터 보안 → 위치 수집 "예" 로 변경
2. 개인정보처리방침(k2bact.github.io/privacy.html)에 명시
3. 원치 않으면 GMA SDK 설정 플래그로 수집 비활성화
```

3번 플래그는 업데이트된 SDK 에 들어오며, 구글이 *"detailed technical integration
guides"* 를 별도 공지로 보낸다고 했습니다. **그 공지가 오면 이 항목에 링크를
추가하십시오.**

#### 켤 이유는 없어 보입니다

위치를 주면 광고 지역 적합성이 올라 단가에 도움이 될 수 있습니다. 그러나
**스도쿠 게임이 위치 권한을 요구하면** 설치 전환율이 떨어지고 데이터 보안 신고가
복잡해집니다. 단가 몇 푼과 바꿀 거래가 아닙니다.
